# `brg` commands

`brg` is also installed as `borgchart`. A **team** is a folder holding `team.yaml`; an **instance** is a team running in one working folder, with its members, messages and notes ([concepts](concepts.md)). `brg create <team> [folder]` makes an instance; `start`, `stop` and `delete` act on it, and are safe to repeat.

**Naming things.**
- **A team** is a path to its folder (starting with `/`, `./`, `../` or `~/`) or a name looked up in the search paths of brg's configuration (`teams:` in `~/.config/borgchart/config.yaml`, or `$BORGCHART_CONFIG`; see [the format](format.md#configyaml)). Two folders with one name are refused, listing both; `teams/x` without `./` is refused with that hint.
- **An instance** is `<team>-<suffix>` (`dev-team-k3f9`), and a **member** `<role>-<suffix>` (`lead-q8m3`). A bare name is a role; only `create` takes one. Every member command and message refuses a role name, listing its kept members (including stopped ones) or naming `brg create <instance>/<role>` when it has none. Outside a member, name the instance in full: `dev-team-k3f9/lead-q8m3`. Inside a member, a bare member ID means its own instance (`$BORGCHART_INSTANCE`). brg never guesses an instance from a team's name or from which instances run.
- **A nested copy** has its full path as its instance ID, for example `oncall-h4k2/dev-a7k2`. Addresses resolve the longest registered instance prefix: `start oncall-h4k2/dev-a7k2` starts the copy, `stop oncall-h4k2/dev-a7k2/lead-c4nd` stops just its lead, and `create oncall-h4k2/dev-a7k2/helper` creates an agent member inside it. Copies can contain further copies. Every address segment must be a valid ID; empty segments, `.`, `..`, absolute paths and trailing `/` are refused before reading the registry.
- **Bus commands** (`msg`, `inbox`, `bus`) take `--instance ID`. It is required outside a member; inside one, it can only repeat the member's own instance.

**Completion.** `BRG_COMPLETE=<shell> brg` prints the shell's registration (bash, zsh, fish, elvish or powershell). Load it when the shell starts, so it always matches the installed brg: in fish, put `BRG_COMPLETE=fish brg | source` in `~/.config/fish/completions/brg.fish`; in bash, `source <(BRG_COMPLETE=bash brg)` in `~/.bashrc`. On each tab press the shell runs brg with the same variable, and brg prints subcommands, flags, team names, instance IDs and `<instance>/<member>` addresses of kept members. It reads brg's records without a lock, so a tab press writes nothing and starts nothing. It uses `clap_complete`'s dynamic completion, which is outside semver; reload the shell after upgrading brg.

`brg <command> --help` documents each command. The bus pages cover message submission and examples (`send --help`), all unacked messages (`inbox --help`), the one wait and its outcomes (`inbox wait --help`), and store health (`bus check --help`).

| Command | What it does |
| --- | --- |
| `brg validate <team> [--json] [--probe]` | Check the team folder and brg's configuration without starting anything; `--probe` also lists each vendor's MCP connectors (this starts your MCP servers) |
| `brg create <team> [folder]` | Make a new instance of the team working in `folder` (the current folder by default; it must exist), usually the repository it works on; start its `start: true` roles and plugin processes, and print its ID and tree. Run it twice and you have two instances |
| `brg create <instance>/<role> [--name <name>] [--branch <name>] [--repo <name>]` | For an agent role, make and start the next member (`<role>-<suffix>`) up to the role's `max` (default 1). `--name` makes the new member's or copy's ID `<role>-<name>`, named for its task: lowercase letters and digits in words joined by single hyphens, at most 24 characters, never a role's name or an ID the instance issued before. For a team role, make a stopped nested copy; start it with `start <instance>/<copy>`. For a `worktree: true` role, brg first adds the new member's or copy's git worktree, on the new branch `--branch` names or detached at the folder's `HEAD`, and prints a line naming it, `<instance>/<member>  folder <path>` (as `create <team>` and a full `start` do for each worktree they add). With `--repo`, select a real clone directly in the tree's top folder and start at origin's fetched default tip instead (below). Both flags require a role with `worktree: true`. Kept members and copies count, running or stopped. At the limit, list them and refuse; for `max: 1`, point to `start`. A child needs its parent role to have a member |
| `brg start <instance>` | Bring the instance to what should run: the `start: true` roles, members running at its last stop, and copies that were running, recursively. Stopped copies stay stopped. A copy that fails to start is reported alongside the others' results. Running members are left alone. A worktree it adds for a new member is named after the tree, `<instance>/<member>  folder <path>`. Members that start use current files and configuration. An unfinished cascade must be completed with `stop` first |
| `brg start <instance>/<member>` | Start that member again, or say it is already running |
| `brg start <instance>[/<member>] --resume` | Start as above, but reopen each member's last vendor session (Claude `--resume`, Codex `resume`) instead of a new conversation, with a short note that its last turn may have been cut off. Every member's SessionStart hook records its session when it starts. A member started on its own with no recorded session is refused; a whole instance starts such members fresh and says so, as it does a member whose role changed vendor since its session. Copies the start restores resume too. A fresh `start` replaces the recorded session once the new one reports in, so resume before starting fresh. A resumed conversation keeps the opening prompt it started with: changes to the role's prompt or commands since then reach it only through a fresh start |
| `brg start <instance> --team <path>` | Point a stopped instance at its team folder's new place (the same team name), keeping its ID and messages |
| `brg stop <instance>[/<member>]` | Stop one member or the whole instance. Every full stop marks the instance and all its copies `stopping`, then stops deepest first, including instances with no copies or team roles. `create` and `start` anywhere inside are refused until the cascade finishes. Unknown liveness keeps the mark and the folder held. Run `stop <instance>` again to finish an interrupted cascade; a second stop keeps the record of who ran |
| `brg stop -r <instance>/<member>` | Stop the member and its recorded subtree deepest first, including copies. A member caller may target descendants, never itself. Holds the registry lock for the walk, so other lifecycle changes wait. Stops at the first failure before ancestors; repeat the command to finish. Each stopped member is removed from the next full-start snapshot. With an instance target, this is the existing full stop |
| `brg delete <instance> [--force]` | Remove a stopped instance: its notes, state and registration. Refused unless every member is certainly stopped and its cascade is finished (`--force` never overrides this). Kept copies must be deleted first. Unacked messages to its kept members, unacked external replies at the root, and unreadable storage need `--force`. Copy history stays readable in the tree store and stops counting as pending work; deleting the root removes the store. The working folder is never touched |
| `brg delete <instance>/<member> [--force]` | Remove a stopped member's live state, reserving its ID forever within the instance. Its incoming unacked messages are listed with a count and need `--force`; unreadable storage also needs `--force`. Its clean worktree is removed; a worktree with uncommitted work or commits on no remote refuses the delete, and with `--force` stays as it is. Running or unknown liveness is always refused. Kept children and team copies recorded under the member, running or stopped, are refused even with `--force` and listed by full address; delete them first. Immutable messages remain as history; messages to a deleted member no longer count as pending work and new ones are refused. `create <instance>/<role>` issues a new ID; `start <instance>` also replaces a deleted member of a `start: true` role. |
| `brg reset <instance>` | Stop a whole tree and forget it, so `brg create` starts it fresh. It takes a root instance only; a copy is refused, and so is any caller inside a member. It first prints that the tree's notes and messages will be deleted, then stops the tree, then deletes every registration in it and the root's state folder (all copies' state, the notes and the tree's messages), and removes the clean git worktrees brg added for its members and copies, by `cleanup`'s rules. The root's own checkout is never touched. Open, unread or undelivered messages and kept copies never refuse it, and there is no prompt. If brg can't confirm that every member stopped, nothing is deleted. Working folders, checkouts and other worktrees are left as they are. It ends with the `brg create` command that starts the tree again under a new ID. If some folders couldn't be checked or removed, the tree is still forgotten, but reset says which and exits 1 |
| `brg cleanup [<instance>]` | Remove what brg left behind for deleted members and copies, found from its records only. Removed: the git worktree brg added for each one, when no registered instance, kept member or copy works at or inside it; and their leftover state from an interrupted `delete`. The worktree is removed with `git worktree remove`, never forced, when it is clean: no other repository or worktree inside it (ignored folders included); nothing modified, staged, untracked (ignored files aside) or marked skip-worktree or assume-unchanged; and no commit from its HEAD, HEAD reflog or `refs/worktree/` refs that no remote-tracking ref reaches. Each git command has 60 seconds. Left and listed: a worktree with work in it. A worktree git can't check is left, and the run exits 1. Without an instance, it also removes state folders named for instance IDs brg issued that are no longer registered. With an instance, it works only there and in its copies. Work folders, kept members' and copies' worktrees, other worktrees and messages are never touched. Exits 1 if anything couldn't be checked or removed |
| `brg ls [--json]` | The teams in the search paths, each with its instances (running or stopped), then instances of teams elsewhere. Copies remain listed as registered instances with their full nested IDs and working folders |
| `brg status [<instance>] [--json \| -w \| -i]` | Show an instance tree, or, bare, every top-level instance with its copies nested once beneath their parent members. Each copy shows its team and how many of its own members run, with those members beneath it. A header names the instance, its team folder and its working folder; on a terminal (and in `-i`, and in the tree `create` and `start` print) it names the instance and its working folder, with the home folder as `~`. Members show vendor, model, state, positive unread count and details. On a terminal (and in `-i`) the vendor is its one-cell mark, `§` for Claude and `Λ` for Codex, as in `§ opus high`, and a member with no declared model shows the mark alone; piped text keeps `claude opus high`. A `working` or `blocked` member's details lead with its activity: what its session is about, in its vendor's own words (below). A member at folder trust is `blocked (folder trust)` with its `brg attach` command. An agent or team role with no member or copy shows `not created (start: false)` or `not created (start: true)` for `max: 1`, or `on demand (none created)` for `max > 1`. On a terminal (and in `-i`) these rows of `start: false` roles are left out, unless a shown row hangs beneath one; piped text and `--json` keep them. A name in italics is a role with no member yet. Plugin processes follow their instance's members. `--json` gives the same tree order; every row's `instance` is its full instance path. Rows carry `kind` (`member`, `role`, `copy` or `plugin`), `name`, `team`, and applicable `member`, `role`, `parent`, `start_id`, `model`, `liveness`, `unread`, `worktree` (for a member or copy of a `worktree: true` role) and `activity` (for any live member, idle ones included). Readable copy rows carry their own instance path and a numeric `running` count, excluding deeper copies. An unreadable copy keeps its row with `state: unreadable`, its error in `detail` and no running count. Parents within an instance are local member IDs; a copy's parent is a full member address, and its root members point to the copy's instance path. `start_id` is retained after stop and changes on restart. Unread counts for the whole tree come from one store snapshot, including zero for readable counts. An unreadable store omits counts and adds a check note; a busy store asks for a retry. On a terminal, columns are name/tree, state, vendor/model or team, then details. A single `borgchart` summary band above the tree puts rows needing you first, followed by working and idle members and unread messages. Piped text retains its original column order and has no band; piped `-w` keeps its summary under the tree. Painted output uses teal for working members and their summary count, a padded filled red label for attention states and the need-you count, and a gold `◆` for running nested teams. State words and marks carry the meaning as well as colour. On a terminal, `NO_COLOR` keeps the terminal layout and state marks, unpainted; it suppresses filled labels and motion. `-w` refreshes the data every `--interval` seconds and shows the last refresh time in UTC; on a painted terminal it redraws in place without clearing the whole screen. In `-w` and `-i`, working rows share a braille spinner that advances every 100 ms; it stops when none are working. In `-w`, frames that fill or exceed the terminal height redraw only at the data interval. `-i` shows the same tree and summary in a rounded grey border with a bold title and grey key help (j/k move, Enter attach, tmux prefix then `d` return, `a` show or hide the roles left out, `r` refresh, `q` or Esc quit). Bare screens pick up instances created or deleted at the next refresh. Enter attaches to the selected member in its own instance; copy and role rows do not attach |
| `brg secret <team> [--json]` | List the secrets the team's plugins need and whether each is set in your environment. Prints no values and writes nothing |
| `brg attach <instance>/<member>` | Open a member's live session; detach with brg's tmux prefix, then `d`. brg's tmux server runs without your own tmux config unless brg's configuration sets `tmux.user_config`, and a change to it applies only once every instance on brg's server has stopped and the server starts again. To keep your own bindings without a restart, attach from inside your own tmux; brg's prefix is then tmux's default, Ctrl-b (press it twice if your own prefix is Ctrl-b too) |
| `brg logs <instance>/<member> [-n LINES]` | Show recent output of a member, or of a plugin process (`<instance>/<plugin>`) |
| `brg send [--external NAME] TARGET TEXT [--reply-to ID] [--force] [--from MEMBER] [--json]` | Record a message, then optionally type it; `TEXT` may be `-` for stdin. Outside callers must name `--external NAME`; members retain their fenced identity. A member reaches a copy's root, or a copy's root its parent, with the full `instance/member` address; the same tree store and typed or locked delivery rules apply |
| `brg inbox [--member ID \| --external NAME] [--full] [--json]` | List every unacked message to you, oldest first; --full includes bodies. --member accepts a bare ID in the caller's or --instance instance, or a full address anywhere in the tree. Reading never acknowledges |
| `brg inbox wait [--external NAME] [--timeout SECONDS] [--full] [--json]` | One scan of the tree store, then incremental reads: new unacked messages return at once, existing messages after 60 seconds only if still unacked. Errors also wait at least 60 seconds; fenced/help/signals are exempt. Timeout 60–86400 seconds, default 86400, exits 9. A stopped/exited/replaced member exits 8 (`fenced`); stop waiting. Store lock attempts respect the deadline |
| `brg msg read ID [--json]` | Show one message in full, including an acknowledged one |
| `brg msg ack ID… [--external NAME] [--json]` | Acknowledge messages addressed to you; acking twice is a no-op |
| `brg bus check [--json]` | Check the store for gaps, unreadable files and stray temporaries; never writes |

**Creating from a folder of clones.** Use one dev copy per repository; the root lead sequences copies:

```sh
brg create <root>/dev --repo widgets --branch fix-rounding
brg create <root>/dev --repo gadgets --branch fix-rounding
```

`--repo` accepts one immediate child name in the tree's top folder. The child and its `.git` must be real directories: paths, symlinks, linked worktrees and bare repositories are refused. brg asks `origin` for its current default branch (including `master` or a renamed default) and fetches it before the registry lock and before issuing anything. Missing origin, unavailable credentials or network failures refuse creation. Fetch uses the caller's credential configuration with terminal prompting disabled. The original clone's working files, index and checked-out branch stay as they are. Creation prints the repository and short commit, for example `· widgets at 3f2a91c`. Without `--repo`, the start remains the instance folder's `HEAD`, so an implementer inside a dev copy inherits that copy's committed work. Clean worktrees delete without `--force`; deletion, cleanup and reset find their repositories through Git's own records, ignoring child `.git` files and refusing duplicate ownership.

## Runtime

- **tmux:** brg runs its own tmux server (`tmux -L borgchart`) with its own config; your `~/.tmux.conf` is read only with `tmux.user_config` in brg's configuration. Each instance is one session, `brg-<instance>`, with one window per member and per plugin process (`_<plugin>`).
- **Folders:** members start in the instance's working folder, or in their own git worktree for a `worktree: true` role. brg's own files live in the instance's state folder (`$XDG_STATE_HOME/borgchart/<instance>/`, or `$BORGCHART_STATE_HOME/<instance>/`): `notes/` and brg's private files, plus `messages/` at the tree root only. All copies share that root store. A working folder that is the same as, inside or around brg's state folder is refused (brg's worktrees live beside it, in `<state>-worktrees/`), and so is a `locked` member's folder around the team folder; a state folder under `/tmp` is refused.

- **Copies:** copies share the instance's folder unless their role sets `worktree: true`; then brg adds each new copy its own git worktree when it issues it (`create`, or a full `start` that gives a `start: true` role a new member), detached at the folder's `HEAD` or on `create --branch <name>`, and `delete` removes it when clean. Starting an existing member never adds one.
- **Member lifecycle callers:** a person may act on anything. A member at its latest running start may create, start, stop or delete members and team copies anywhere in its subtree. Authority follows recorded parent edges within an instance and across copies; the caller's start is checked in its own instance under the registry lock that covers the change. Members cannot manage themselves, ancestors, siblings or independent instances, or create independent teams; ask a person, or declare a team role and use `brg create <instance>/<role>`. A copy's roots cannot manage their own copy or each other. Stopped, replaced and incomplete starts are refused. Creating a child requires a kept parent member. Parent roles and plugin `delivers_to:` targets must name agent roles with `max: 1`.
- **Checkouts:** a start is refused when a member's folder is the same as, inside or around a folder another instance holds: one of its members runs there, brg can't tell that member stopped, or the instance has an unfinished stop cascade. A fully stopped instance holds no folder against other instances. Different roles of one instance may share a folder.
- **Permissions:** Codex `vendor` members run with `--sandbox danger-full-access --ask-for-approval never`; Claude `vendor` members get `messages/` and `notes/` through `--add-dir` unless their own args replace those added folders. Locked members keep their existing gate and writable-folder restrictions.
- **Environment:** windows start with a small environment copied from your shell (`PATH`, `HOME`, `LANG`, `TMPDIR`, `XDG_*`, `BORGCHART_CONFIG`, …), plus what each needs: `BORGCHART_INSTANCE`, `BORGCHART_MEMBER`, `BORGCHART_ROLE`, `BORGCHART_NOTES`, `BORGCHART_BIN` and the current start ID `BORGCHART_INCARNATION`. Copy roots' windows also get `BORGCHART_PARENT`, their parent's full address. With `auth: api_key`, each member gets its own vendor's key (`ANTHROPIC_API_KEY` or `OPENAI_API_KEY`) by name; with `login`, neither. Plugin secrets come from the environment `create` or `start` runs in, live only in 0600 files in the instance's state folder, read by brg's shims, and are removed at `brg stop`. 0600 keeps other users out, not members: a member that isn't `locked` could read the file while it exists.
- **Plugin actions:** shims require the invoking member's own launch identity and preserve its incarnation. Missing, mismatched, stopped or replaced identities are refused before the action runs; direct operator invocation is refused too. Store identity must be readable.
- **`locked` start-up check:** a `locked` member's gate must report in when it starts. If it doesn't, or the member stops at any prompt first, the start stops it rather than let it run unprotected. The one exception is its vendor's folder-trust screen (Claude or Codex): the start leaves it there and says to attach. brg never answers Codex's, and answering either yourself is your decision to trust that folder; `send` still refuses the member until its gate reports in.
- **Inactive gate:** `send` refuses any `locked` member whose gate has not reported in, and `status` shows it as `gate-inactive`.
- **Copy mode:** a member's pane that tmux has in copy mode (or another mode, after scrolling back in `brg attach`) would send keys to tmux, not the member. So `send`, the wake and a start's folder-trust answering type nothing into it until it leaves that mode (usually `q`), and `status` adds that to the member's details.

## States

`status` reads each member's state from its screen with per-vendor rules (bundled; override in `$XDG_CONFIG_HOME/borgchart/rules/<vendor>.yaml`):

| State | Meaning |
| --- | --- |
| `idle` | Waiting for input |
| `working` | In a turn |
| `blocked` | At a prompt that needs a person (a permission, a question); `blocked (folder trust)` at its vendor's folder-trust screen, with the detail "waiting at folder trust: `brg attach <instance>/<member>`" (`--json` keeps `"state": "blocked"` with `"rule": "trust-dialog"`) |
| `unknown` | Running, but no rule matched (e.g. after a vendor update changed the screen) |
| `gate-inactive` | A `locked` member whose gate hasn't reported in; it gets no input |
| `exited` | The program ended (with its status when tmux knows it) |
| `not created (start: false)` or `not created (start: true)` | A role with no member yet (a row with `kind: role`), following its `start` setting |
| `on demand (none created)` | A `max > 1` role with no kept members |
| `not started` | A member that has never started in the instance |
| `stopped` | Ran and has ended; printed `stopped (should be running)` for a `start: true` member while the rest of the instance runs, with `"expected_running": true` in `--json` |
| `stopping` | An instance or copy has an unfinished stop cascade; run `brg stop <instance>` to finish it before creating or starting inside |
| `unreadable` | A kept copy could not be read; its detail shows the error. Other readable members and copies remain visible in text, JSON, watch and interactive status |

States are advisory: they gate `send` for safety, not access.

### Activity

A vendor's rule file may also say where its terminal title describes the session. Claude Code titles its terminal with its own short summary of the topic, so a working Claude member reads, for example, `working  Review open GitHub issues`. It is the session's topic, not its current step, it changes when Claude Code retitles the session, and it is cut at 60 characters. Codex's title names the folder, so Codex members show none. The text is the agent's own: treat it as a label, not a report. The rule is `activity:` with a `title` pattern whose first capture group is the text, and optional `none` patterns that discard it:

```yaml
activity:
  title: '^\S (.+)$'
  none: ['^Claude Code$']
```

Stopping an instance continues through its readable copies even when another copy's
state is unreadable, then reports the unreadable copies and exits non-zero. Restore
their state and retry `stop` to finish the cascade. Kept copies, including unreadable
ones, must be deleted before deleting their parent instance. If the recorded tmux socket
is absent or refuses connections, its windows are gone: members with no recorded
process, exited processes, or starts recorded under a different machine boot let
the cascade finish. A single-member or `-r` stop also succeeds when the recorded server
is absent for a member with no recorded start, an ended start or an old-boot start.
Each start stores the Linux boot ID or macOS boot-session UUID; a missing or unreadable identity remains conservative. Reachable live panes
still count as alive. A surviving or unconfirmed same-boot process keeps it marked; the refusal names the member and PID to end
before retrying `brg stop <instance>`. Other server errors keep it marked: fix the
reported error, then retry `stop`. Stopping a copy separately removes
it and its descendants from every ancestor's next full-start restore list.

## `brg send`

- **Identity and route:** outside callers must use `--external NAME`, even without expecting a reply. Members cannot use it and send only to their parent or children; only root members of the tree's root instance may send to `external:NAME`. Across a copy's parent edge, use the full `instance/member` address. The tree shares one store and numbering; typed and locked delivery use the recipient's own pane and guards across edges too. Sibling, cousin and independent-tree routes refuse. Lifecycle subtree authority does not widen message routes. `--from MEMBER` asserts a parent route within one instance, not authorship: members must name themselves; external relays stay `external:NAME` and their envelope says “relayed for MEMBER.”
- **Durable first:** ordinary sends commit before optional typing. `interactive: true` recipients are inbox-only, even with `--force`; roles default to false. Stopped recipients, drafts and blocked input can leave a record stored. Code 0 means the ordinary record committed, including uncertain typing; never republish automatically because it was not typed.
- **Guarded input:** one tagged bracketed paste followed by Enter, including while Working. Re-read the exact incarnation/pane and preserve drafts. Visible dialogs and copy mode prevent input; unknown state needs `--force`, which does not override other guards. Recheck exact composer contents before Enter. No guarantee closes the race after that check, or orders concurrent typing.
- **Screen verification:** wait up to three seconds for paste rendering and for submission after Enter. Envelopes over 1024 bytes or ten estimated screen lines (also limited to half the captured pane rows) are not pasted. This conservative ASCII-width estimate is not a vendor limit; wide or combining characters can fail exact verification after paste. Ordinary messages remain stored, while locked delivery refuses before commit. Never clear a draft automatically. If verification leaves text behind, the recipient or a person controlling its pane must inspect it before further input; senders without pane access should notify that owner.
- **Text and references:** at most 16 KiB of body, plus bounded envelope bytes; newline and tab are allowed, other controls and leading `/` or `!` refused. `TEXT` of `-` reads stdin. Repeat `--reply-to ID` for existing tree-wide message IDs (up to 32), with plain references such as `m1`.
- **Acknowledgement:** ordinary recipients explicitly `msg ack ID` when taking responsibility. Typing never acks; ignore an already-acked duplicate from an inbox wait. Message content retains the sender's authority, not the owner's authority.
- **Locked:** preflight the live gate/pane, empty composer and typing budget before recording. Its immutable `ack_required: false` record is typed-only and gets no ack hint or new grants. A postcommit typing failure is nonzero with its ID; retry may duplicate history and uncertain input. There is no inbox recovery.
- **JSON:** retains `ok`, `code`, `message`; adds `outcome`, committed `id`, `delivery` (`typed`, `stored`, `uncertain`, `recorded-not-typed`) and reason.

| Code | Outcome | Meaning |
| --- | --- | --- |
| 0 | `committed` | Ordinary record committed, or locked record committed and submitted; not proof of accepted work |
| 2 | `usage` | Syntax/flags or missing outside identity |
| 3 | `not-alive` | Unaddressable target, or locked target not running |
| 4 | `blocked` | Locked dialog or copy mode prevents input |
| 5 | `refused` | Text, identity/fencing, route, reference or storage refusal; locked input failure/uncertainty, with committed ID when present |
